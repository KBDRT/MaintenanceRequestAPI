# REST API «Сервис учёта заявок на обслуживание оборудования»
Стек: Node.js, Express, Typescript, PostgreSQL. <br>
Дополнительно: zod (валидация), sequelize (работа с БД), test/supertest (простые тесты), umzug (миграции и сиды).

Сервис ведёт справочник оборудования и заявки на его обслуживание, контролирует жизненный цикл заявки и позволяет оценить погодные условия на объекте перед планированием наружных работ.

**Рабочая версия с сохранением данных в памяти (Неделя 2) вынесена в отдельную ветку** [stable/week2](https://github.com/KBDRT/MaintenanceRequestAPI/tree/stable/week2)

## Требования к окружению
- **Node.js** версия 20 или выше - запуск утилиты;
- **npm**: - установка дополнительных библиотек из зависимостей;
- **Доступ в интернет** - обращение к внешнему API;

## Инструкция по установке
1. Клонировать репозиторий
```
git clone https://github.com/KBDRT/WeatherDigest
```
2. Перейти в корневую папку сервиса
3. Установить библиотеки из зависимостей
```
npm i
```
4. Создать файл с переменными окружения (.env). [Пример файла (.env.example)](/.env.example)
5. Сбилдить и запустить сервис
```
npm run build
```
```
npm start
```
5.1 Запустить сервис в режиме разработки
```
npm run dev
```

## Модель данных

### Оборудование (equipment)
| Атрибут | Тех. название | Тип | Ограничения |
|:-----------|:-----------|:-----------|:-----------|
Уникальный идентификатор|id|string|uuid, генерируется сервером
Название|name|string|3–100 символов, обязательное
Тип|type|string|Допустимые значения: turbine,inverter,sensor,ubstation
Серийный номер|serialNumber|string|Уникальный в пределах системы
Расположение (координаты широты и долготы)|location|Объект с полями: lat, lon|Значения lat, lon - числовые
Статус|status|string|Допустимые значения: operational, maintenance,fault,decommissioned
Дата установки|installedAt|string|Формат ISO-дата, не в будущем

### Заявка на обслуживание (maintenance request)
| Атрибут | Тех. название | Тип | Ограничения |
|:-----------|:-----------|:-----------|:-----------|
Уникальный идентификатор|id|string|uuid, генерируется сервером
Идентификатор связанного оборудования|equipmentId|string|uuid, существующее оборудование
Заголовок|title|string|5–120 символов, обязательное
Описание|description|string|до 2000 символов
Приоритет|priority|string|Допустимые значения: low, medium, high, critical
Статус|status|string|Допустимые значения: new, in_progress, done, rejected
Запланированная дата|plannedAt|string|Формат ISO-дата, необязательное
Дата создания|createdAt|string|Формат ISO-дата, генерируется сервером
Дата обновления|updatedAt|string|Формат ISO-дата, генерируется сервером

### Ограничения изменения статусов заявки
При создании заявки, ее статус отмечен как новый (status = new).
<br><br>
Допустимые изменения статусов заявки пользователем, в зависимости от старого статуса:
- new → in_progress
- in_progress → done
- new → rejected
- in_progress → rejected

## Формат ошибок
Все ответы об ошибках имеют единый формат, где requistId - уникальный номер запроса, для возможности поиска ошибок в логе.
Пример ошибки валидации:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные запроса",
    "details": [ { "field": "priority", "message": "Недопустимое значение" } ],
    "requestId": "b1f2c3d4"
  }
}
```

## Безопасность

### CORS
Список разрешенных источников задается в переменной окружения ```CORS_ORIGINS``` (через запятую). Учитывается только в режиме ```NODE_ENV = production```. 
Позволяет ограничить доступ к API, контролирует список разрешенных источников, которые могут обратиться к сервису.

### Частота запросов
Реализовано ограничение частоты запросов и временное окно для их отправки (через переменные окружения: ```RATE_LIMIT_WINDOW_MS```, ```RATE_LIMIT_MAX_REQUESTS```). При превышении значений, клиент получает 429 с заголовками, заполненными значениями лимтов (Ratelimit-Limit, Ratelimit-Reset)

### Тело запроса
Размер тела запроса ограничивается из переменной окружения ```BODY_JSON_LIMIT```, для сохранения памяти и защиты от атак с большим количеством данных. С помощью helmet настроены защитные заголовки для защиты от базовых угроз.

### Cookie
Для реализации простой аутентификации на основе JWT токена используются куки, в которых хранится токен. Куки являются **HttpOnly: true** для защиты от кражи при XSS-атаках (запрет чтения из скриптов), 
**Secure: true** (в режиме ```production```) для использования только при https подключении, **SameSite: strict** - запрет на передачу cookie при внешних запросов, 
т.к. токен является критичными данными и необходим для аутентификации. 


## Структура проекта

Функции и классы сервиса распределены по [папкам](/src) в соответствии с их областями ответственности.

| Модуль | Описание
|:-----------|:-----------
[/config](/src/config)|Настройка основных параметров и правил сервиса: чтение и валидация переменных окружения с заполнением константных объектов для удобного доступа. 
[/controllers](/src/controllers)|Контроллеры, реализующие эндпоинты API. Получает данные из запроса, вызывает сервисы с бизнес-логикой, отправляет ответы клиенту.
[/domains](/src/domains)|Модели данных сервиса.
[/dto](/src/dto)|DTO (Data Transfer Object) вспомогательные классы и типы (без логики) для передачи данных между внутренними слоями сервиса.
[/errors](/src/errors)|Классы ошибок для конкретных ошибочных сценариев.
[/lib](/src/lib)|Настройка логгирования, предоставление доступа к логу в любых местах сервиса.
[/middlewares](/src/middlewares)|Классы, которые встраиваются в конвейер запросов: Валидация запросов, аутентификация, обработка ошибок, парсер параметров запроса, логирование и другие.
[/repositories](/src/repositories)|Классы для работы с хранением данных для сущностей системы (интерфейс с абстракцией и реализация с хранением в памяти).
[/routes](/src/routes)|Маршруты запросов. Добавление различных middleware в цепочку обработки запросов, сопоставление запросов с функциями контроллеров.
[/services](/src/services)|Реализация основных сценариев бизнес-логики сервиса.
[/validators](/src/validators)|Схемы для валидации данных (библиотека zod).

### 3. Аутентификация 
Для аутентификации используется JWT-токен, которые хранится в HttpOnly cookie. <br><br>
Параметры секретного ключа и время жизни токена задаются в переменных окружения: ```JWT_SECRET_KEY``` и ```JWT_MAX_AGE_MS```.<br><br>
Для реализации аутентификации созданы:
- эндпоинты ```/api/auth/login``` (создание и сохранение токена) и ```/api/auth/logout``` (удаление токена); 
- контроллер [auth.controller.ts](/src/controllers/auth.controller.ts) с реализацией логики данных эндпоинтов;
- middleware [auth.middleware.ts](/src/middlewares/auth.middleware.ts), который используется для запросов с изменением сущностей: ```POST```,```DELETE```,```PATCH```, в котором проверяется токен и его валидность;
- класс ошибки [authentication.error.ts](/src/errors/authentication.error.ts)

**При ```NODE_ENV=development``` токен не проверяется.**

При отсутствии токена или его невалидности - ```401 Unauthorized```.

### 1. Мягкое удаление paranoid

Для мягкого удаления выбрана сущность **оборудование** (Equipment). По умолчанию поле серийного номера (serialNumber) было ограничено на уровне БД уникальностью (unique). <br>
После включения в таблице мягкого удаления (paranoid: true) в ней появляется дополнительное поле deletedAt. После удаления оборудования запись в таблице не исчезает, а помечается заполнением поля deletedAt с меткой времени. В выборках запись не используется, а для ограничения уникальности серийного номера был создан индекс и отключено свойство unique у поля serialNumber, которое учитывало бы удаленные записи по умолчанию. <br><br>

Для проверки следует отключить проверку уникальности серийного номера на уровне сервиса [equipment.service](src/services/equipment.service.ts) <br>

Созданние индекса:
```typescript
addIndex('Equipment', {
    name: 'uq_equipment_serial_active',
    fields: ['serialNumber'],
    unique: true,
    where: { deletedAt: null }, 
  });
```

Добавление индекса вынесено в отдельную миграцию [008-create-equipment-index](src/migrations/test/008-create-equipment-index.ts). 

При попытке добавления существующего серийного номера, ошибка от БД:

### 2. Поиск по текстовым полям

Реализова поиск по текстовым полям средствами PostgreSQL с использованием ILIKE и индекса. <br><br>
Для этого используется расширение **pg_trgm** и индекс типа GIN (Generalized Inverted Index), которые позволяют хранить в индексе триаграммы (в индексе хранятся части по 3 символа каждого текстового поля).
Вместо полного перебора, выборка использует данный индекс с триаграммами и ищет совпадения по ним.
В качестве используемого текста выбрано поле описание (description) из таблицы MaintenanceRequests.

Установка расширения и создание индекса вынесено в тестовую миграцию [009-create-ilike](src/migrations/test/009-create-ilike.ts). <br>

Для проверки использования индекс создан сид [008-create-test-requests](src/seeds/test/008-create-test-requests.ts). В нем поле description заполняется случайными числами от 100 до 1000001.

Результат следующей выборки на 10000 записей:

```sql
SELECT id, description FROM public."MaintenanceRequests"
WHERE description ILIKE '%111%'
ORDER BY id ASC
```
